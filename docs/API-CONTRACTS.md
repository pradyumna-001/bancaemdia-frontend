## Regras de integração

1. Contrato pinado com SHA/hash e estado da capacidade; nenhuma resposta de domínio definida manualmente para antecipar API.
2. Não usar read model de outro filtro para preencher cabeçalho financeiro, nem sumarizar páginas/grupos no cliente.
3. `Idempotency-Key` conforme endpoint/intenção; timeout após envio não prova falha de gravação. Retry não cria nova intenção.
4. Diferenciar sem dado, desconhecido, não aplicável, pendência de revisão, dado antigo e zero válido.
5. Existe ensaio de integração no backend #155 com patches/SHAs e testes de billing/metas; ele não é release. Preservar esse trabalho ao adotar a API integrada e testar experiência web separadamente.
6. Não adicionar URLs secretas/códigos/tokens a logs, query params ou snapshots. Sessões de demonstração só em fixture isolada.
7. Issue #50 coordena lacunas por unidade; antes de abrir backend issue, verificar implementação/issue vigente para não duplicar função existente.
8. Browser autentica por cookie HttpOnly (`credentials: include`), CSRF apenas em memória; não recebe/injeta JWT externo. O PR #168 reutiliza validação numérica no servidor. Proxy deve encaminhar `/auth/*` e `/api/*`; ver [ADR003](adrs/003-api-client-typing-session.md) e [prova/pendências](identity-validation.md). Não promover schema de PR ao cliente público como contrato integrado.
9. #9 entrega [transporte tipado](contracts/cliente-api.md) da main pinada: manifesto commit/hash, tipos e políticas gerados juntos, cookie/CSRF sem tokens, deadlines/cancelamento, erros seguros e formatos próprios. `POST /caixa` é a única operação idempotente dessa versão; upload/planilha são multipart. Downloads e null são preservados. Disponibilidade financeira ampliada/billing/sessão/telas continua conforme as linhas e consumidoras acima.
10. #10 entrega [recuperação contextual](contracts/recuperacao.md), campos 422 sem payload privado, paginação com limites do mesmo snapshot e tentativas limitadas por recurso. 409 sem motivo publicado não é tratado automaticamente como dado velho; 401 não se confunde com 402. Componentes/fixtures não publicam sessão, billing, prévia ou telas futuras.
11. #24 implementa [Enviar export do Telegram](contracts/enviar.md): POST único multipart, 202/UUID na URL e acompanhamento da #15; resposta ambígua exige leitura separada e nova seleção explícita. Prova de importação usa API/worker/banco reais e apenas entrada de extração em cache, sem chamada paga; não é deploy nem certificação de qualidade da IA.

12. #54 implementa [Conexão Telegram](contracts/telegram.md), com código somente em memória, polling finito e revogação confirmada sob READ_ONLY. O endereço do bot continua pendente de lançamento por decisão do dono; link fictício é interno e explícito. Prova de SPA/API/banco usa transporte privado local IncomingCommand, sem Telegram externo; sandbox não é lançamento.
